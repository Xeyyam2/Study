# Taste

## Workflow
- Strongly prefers strictly sequential execution: finish one unit (file, language, task) completely before starting the next; explicitly forbids parallel batch processing. Confidence: 0.9
- Wants a short summary after each completed unit of work and a final summary table at the end of a multi-step task. Confidence: 0.8
- Prefers the assistant to make cultural/contextual judgment calls autonomously rather than interrupting with questions. Confidence: 0.9
- Continues through the remaining steps of a multi-step task autonomously (e.g., next language/file) without waiting for an explicit "continue" command, unless the user explicitly stops. Confidence: 0.8
- Uses todo lists to track multi-step tasks and marks progress per step. Confidence: 0.7
- Before starting a large multi-part task, wants a brief scope confirmation first (how many items, which cities/topics, source choices), then autonomous execution. Confidence: 0.8
- Expects the brainstorming skill to be used to produce a plan/spec for content or design expansion tasks before implementation; explicitly asks for it ("brainstormingden istifadə edərək" / "brainstroming den istifade eliyerem") and expects brainstorming to precede coding. Confidence: 0.95
- Has a planning/audit-driven workflow: maintains a phased fix list (duzelis.md) whose completed phases may be marked done while their work is still uncommitted in the working tree; when executing a later phase, verify diffs of touched files before committing so previously completed-but-uncommitted work gets included in the commit. Confidence: 0.8
- Project shell environment is Windows (cmd/PowerShell): bash heredocs fail for multi-line commit messages, but PowerShell accepts a multi-line `git commit -m "...\n\n..."` string directly (observed working); writing the message to a temp file and committing with `git commit -F <file>` is the fallback when quoting gets messy. Confidence: 0.7
- Never run destructive git commands (`git checkout -- <path>`, `git clean`, `git reset --hard`) on paths that may hold uncommitted work — always verify with `git status`/`git diff` first; uncommitted user work in this repo is common and is assumed precious. Confidence: 0.6
- For repetitive multi-file edits (e.g., adding one key to many JSON/i18n files), prefers a small Node script with line-based insertion that preserves the original file formatting — a JSON parse/modify/round-trip rewrite is unacceptable because it reformats entire files and creates huge diffs. Confidence: 0.6
- Maintains the project plan/fix list in a markdown file (e.g. duzeli.md) with numbered phases and checkbox status markers ([✓]/✅ done, [•] in progress, [ ] pending); expects the assistant to read that file and execute the remaining unchecked/in-progress items. Confidence: 0.85
- Expects the assistant to apply senior-level expertise across frontend, UI, QA, backend, and SEO disciplines when executing a multi-phase implementation — e.g. explicitly asked to fix phase-4 SEO items "as a senior SEO" (senior seo olaraq duzelt) — and also when starting new feature work ("start coding as senior fullstack, senior frontend, senior UI, senior backend, senior SEO"). Confidence: 0.85
- Prefers pragmatic, YAGNI-driven decisions over large speculative refactors: when an audit offers a "remove misleading config" vs "full rewrite" choice, pick the minimal correct fix; skip features that would need external service credentials (Sentry DSN, Upstash Redis) rather than blocking, and defer them with a clear note. Confidence: 0.8
- When a review/test exposes dead code (e.g. an option field never populated by the data layer, a misleading test name, a failing stale test), removes or corrects it rather than preserving it for compatibility. Confidence: 0.8
- When a build failure is caused by a service that is simply down (e.g. Postgres unreachable — ECONNREFUSED), the accepted fix is to bring the infrastructure up (start the Docker container, run migrations, verify seed data) and rebuild, not to paper over the failure with code-level workarounds. Confidence: 0.6
- Accepts the assistant acting as an ops/DevOps engineer on their machine: starting Docker Desktop via PowerShell, starting/stopping containers, running DB migrations, and inspecting container/table state to unblock a build. Confidence: 0.5
